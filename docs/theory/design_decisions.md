# Design decisions and trade-offs

This page records the trade-offs that Cadwyn has already accepted, the known limitations it lives with, and the rules for changing it. Read it before proposing a change to Cadwyn's behavior. Most of the hard questions here have already been answered, and the answers are usually "do less".

## Why most fixes are breaking changes

Cadwyn's output for an older API version *is* a public API: the clients of the apps built on Cadwyn depend on it, and they can't opt out of a Cadwyn upgrade. So every change to what an older version accepts, returns, or documents in OpenAPI can break a third party, even when the old behavior was a bug. This is why Cadwyn treats the OpenAPI and behavior of every version as a frozen contract, and why fixing long-standing bugs made 8.0.0 a major release.

The maintainer's three principles follow from this:

1. Existing users should almost never get breaking changes.
2. FastAPI and Pydantic features should keep working transparently, but only as far as FastAPI and Pydantic themselves go.
3. Every change should make Cadwyn simpler if possible. Complexity is the main long-term cost: after 8.0.0, `schema_generation.py` is about 4,000 lines and `structure/versions.py` about 2,000.

Cadwyn also doesn't aim for "pay only for what you use". Every app should run roughly the same Cadwyn: prefer one behavior and one code path for everyone over special paths that only some apps take, so that bugs show up for everyone and get fixed once.

## Supported API

Everything importable from `cadwyn` is supported. So are the internals that Airflow's Task SDK builds on, and changing them counts as a breaking change:

* `VersionBundle.versions` and `VersionBundle.reversed_versions`
* the `alter_*_instructions` attributes of `VersionChange`
* calling the instructions in them (`_AlterDataInstruction.__call__`) with any object that has a `body` attribute
* `generate_versioned_models()`, and indexing its result (`SchemaGenerator.__getitem__` from `cadwyn.schema_generation`)

## Costs of the architecture

These follow from how Cadwyn works, which [Architecture](architecture.md) describes, and are not bugs. Changes that try to remove them are almost always rejected.

* **Business logic sees only the latest version.** Older versions are generated copies of the latest models, and migrations are written against the latest models.
* **Older versions use copies, not the original classes.** Cadwyn copies models and changed enums for every version. Code that compares by identity (`isinstance`, `is`, dicts keyed by enum members) can see these copies, e.g. in the first run of a versioned dependency. Objects that can't be deep-copied (e.g. a validator holding a `threading.Lock`) fail when their models are versioned.
* **Requests are validated twice, and dependencies run twice.** A request is validated by its version's route, migrated, and validated again by the latest version's route. Dependencies run in both passes, so their side effects happen twice unless they check `current_dependency_solver`. Uploaded `bytes` files are held in memory twice.
* **Migrations only run for the schema you name.** Request and response migrations run when their schema is the route's own body or `response_model`, or a member of a union that is (only for the requests and responses that are that member), not for that schema nested in other schemas or generics. Schema instructions, on the other hand, change a schema everywhere it's used. This is deliberate: it keeps each migration running exactly once, where it was declared.
* **Cadwyn relies on FastAPI, Pydantic, and `typing` internals.** For example: `solve_dependencies`, `fastapi._compat`, FastAPI's lazily included routers, `FieldInfo` internals, and `typing`'s alias cache. Upstream minor releases can break Cadwyn. The twice-daily workflow upgrades every dependency and runs the tests to catch this. It must always pass, and failures are fixed in Cadwyn, never by pinning or capping a dependency.
* **Startup copies every model for every version.** Copying only changed models would make startup much faster, but it changes OpenAPI names and model behavior. It's too large a change, and it isn't planned.

## Decisions already made

| Area | Decision | Why |
| --- | --- | --- |
| Generic models (`Page[Item]`) | Their type args are always versioned. There is no option to turn it off. | User-reported bug (#416). Options double the test matrix and the code paths. |
| Inherited fields | `schema(Child).field(...)` changes only `Child` and its subclasses. | User-reported bug (#466). |
| Renaming a field in a subclass while a base still has it | Fails at startup with an error that names the base. Rename the field in the schema that declares it, and in the same version in the subclasses that changed it in newer versions. | Pydantic models can't drop the fields that they inherit, so the subclass had both the old and the new field. Renaming it only in the subclass would mean not inheriting from the parent's copy, which breaks the parent's validators and `isinstance` (#525). |
| Renaming a field in a parent while a subclass declares it, changed it in a newer version, or gets it from another base | Fails at startup with an error that names the subclass. Rename it in the subclass, or in the other base, too, in the same version. | The subclass had both the old and the new field. Renaming the subclass's field silently instead would break the apps that already rename it in both, and would guess for subclasses whose other bases have the new name (#581). |
| `didnt_exist` for a field that a subclass declares again or changed, while a base still has it | Fails at startup with an error that names the base. Delete it from the base in the same version. | The instruction did nothing: the subclass inherited the base's field, silently (#582). |
| `Annotated[T, Depends(f)]` | Versioned only in the versions that change the models or enums `f` validates. | Versioning it everywhere gave copies to identity checks in every version (#467). Missing an exotic case (e.g. a recursive type alias) keeps the previous behavior, which is acceptable. |
| Converters of union members (`Union[A, B]`, `Optional[A]`) | 9.0 runs them for the member that the request or the response is: the body that the client's version validates, or the model of the object that the endpoint returns. If Cadwyn can't tell the member, it fails. Migrations of the union itself replace the ones of its members in the same version change. | User-reported bug (#530). Before 9.0, they never ran for unions. Running a member's migration on another member's data would change values silently. Responses aren't validated to find the member: FastAPI validates them again with the client's version's models after the migrations, so their validators would run twice. |
| Converters inside nested models | Won't do. Write the converter for the outer schema. | Running nested converters by default would convert data twice for apps that already follow the docs (#468). |
| Computed fields that return versioned models | Documented limitation. Expose the data as a regular field instead. | Every Pydantic serializer that picks a model by the value's type loses nested JSON config, changes duck-typed values, or re-wraps user exceptions (#469). |
| `.had(alias=...)` and `.didnt_have("alias")` | Since 9.0, they also change the validation and serialization aliases that Pydantic copied from `alias`, like `Field()` does, so the wire key matches the documented one. Data that has the field's old key but not its new one fails (a 422 or a 500) instead of giving the field its default. 8.x only warned at startup. | Clients of apps without migrations relied on the old key, so the fix had to wait for a major release, and it must break them loudly, never by losing their values (#465). |
| Fields whose validation and serialization keys differ | Fix only requests and responses that would certainly fail ("rescue-only"). | Responses that passed before must not change at all, even if they lost a value. |
| Self-referencing models | Copied when that's safe. Otherwise Cadwyn raises `SchemaGenerationError` at startup. | Failing clearly is better than serving wrong shapes silently. |
| Enum defaults of omitted parameters on FastAPI before 0.148 | Not rewritten. | It would fix a pre-existing bug on old FastAPI only, and every attempt added new edge cases. |
| `/changelog`, `generate_changelog()`, and `hidden()` | Removed in 9.0. | Maintenance cost. Apps can now generate a better and more extensible changelog from their version changes themselves, e.g. with a coding agent. |
| Options and flags | Avoided in 99% of cases, including for shipping a breaking fix early. A breaking fix waits for a major release. | Each one doubles the code paths and the tests. |
| Minimum supported versions | Raising the FastAPI minimum to drop compatibility code is fine. The Pydantic and Python minimums are raised only when unavoidable. | FastAPI moves fast and Cadwyn depends on its internals. Raising the Pydantic or Python minimums blocks more users. |
| FastAPI before 0.137.1 | Not supported. | Its router model is different. Supporting both doubles the routing code. |

## Known limitations

These are accepted for now. They are listed so that nobody "discovers" and fixes them as a side quest. A fix for any of them is a separate, deliberate change with its own issue.

* Enum-valued members are unwrapped in generated copies, including values passed to `had()`: for `Outer.a = Inner.a`, the copy's value is `Inner.a.value`, not `Inner.a`. Equal raw values can become aliases. This behavior is retained to preserve existing requests, responses, validation errors, and OpenAPI; define versioned enums with raw values directly (see [Enum migrations](../concepts/enum_migrations.md#how-cadwyn-copies-enums)).

* Generic models keep the latest models in older versions when a type arg refers back to its own model through a quoted annotation, such as `Optional[Page["Category"]]` in `Category`, or when it uses a recursive native `type` alias. A PEP 695 generic model that refers to itself through a quoted annotation, such as `nxt: Optional["Wrap[X]"]` in `class Wrap[X](BaseModel)`, returns a 500 in every version, including the latest one, instead of failing at startup. On Pydantic 2.14.2 and newer, this happens only when a version change alters its type arg.
* Type aliases: native `type` aliases that refer to themselves, directly or through other type aliases, are supported only when they contain nothing but builtin types (such as `str`, `int`, `list`, `dict`, `Union`, and `Literal`) and other such aliases, like `type JsonData = dict[str, JsonData] | list[JsonData] | str | int | None`. The routes that use one that contains anything else, such as a model, an enum, another class, a forward ref, or `Annotated`, fail with a `SchemaGenerationError` that names the alias when Cadwyn generates them. Models in a reference cycle, such as `children: "list[Category]"` in `Category`, that use such an alias fail with a `SchemaGenerationError` when Cadwyn copies them if any version has schema or enum instructions.
* Generic models used without type args: Cadwyn doesn't version the bounds, constraints, and defaults of type params. So the older versions of a generic model used without type args (e.g. `Page` instead of `Page[Item]`), whose `TypeVar` bound, constraint, or default refers to a model or an enum that changes between versions, validate with the latest version of that model or enum (#584). Use the generic with type args, e.g. `Page[Item]`.
* Enums: a strict response model (`ConfigDict(strict=True)`) with a plain `Enum` or `Flag` (`class Kind(Enum)`, not `class Kind(str, Enum)` or `class Kind(IntFlag)`) that has `enum(...)` instructions returns a 500 in every version, because the copies of the enum reject the latest members. A request body with such an enum also returns a 500 in every version when the request's version gets the enum inside pydantic models that Cadwyn doesn't dump, or in a lazily validated `Iterable[...]` field. That's the case for bodies that aren't a single model but hold models (e.g. `body: list[Item]`), and for models or containers that pydantic doesn't make that a request migration puts into the body (e.g. a custom sequence). The latest version gets the members of the copies there. Cadwyn only replaces these members in the `list`, `tuple`, `set`, `frozenset`, `dict`, `deque`, `defaultdict`, `OrderedDict`, and `Counter` values that pydantic makes, including the ones in the dump of a model body, because copying models or iterating anything else could change it or run code of users.
* Dependencies: class dependencies (except Pydantic models) are not versioned. WebSocket routes and streaming (generator or server-sent-event) endpoints don't work in versioned routes.
* Unions of form models: FastAPI 0.153.0 and newer validate every model of the union from the body as if it were form data. So when a validator or a migration puts a list, set, or tuple into a field that one model of the union takes as a single value (e.g. `value: Any`) and another one takes as repeated values (e.g. `value: list[str]`) or as an extra field, Cadwyn can't pass the value so that every model gets it whole:
    * With FastAPI 0.153.0 to 0.160.x, Cadwyn passes the body as it is, like Cadwyn 8.x. A model whose field takes a single value gets only the last item of a list, and a field that takes repeated values gets a set or a tuple as one item. If that model is the one that accepts the body, the endpoint silently gets the wrong value, e.g. `["b"]` instead of `["a", "b"]` from a validator that splits `"a,b"`. Upgrade FastAPI to 0.161.0 or newer to get a clear error instead.
    * With FastAPI 0.161.0 or newer, the request fails with a `CadwynError` that names the field and the models. It also fails if a form model outside the union (e.g. of a dependency override) shares the body and would get a list in a list.
* Request bodies that are lists or dicts of models (e.g. `list[Model]`): the latest version gets the extra keys and set fields that the client has sent only for the models that both the client's version and the latest version have at the same place, inside lists, dicts, and unions without validators, serializers, `Any`, or other schemas around them in either version. The client's version must keep the fields of the latest model with their keys and defaults (defaults that are equal but differ, such as `Decimal("1.00")` and `Decimal("1.0")`, count as changed), neither version of the model may have validators that get the raw input (e.g. `model_validator(mode="before")`) or a custom `__init__`, and each key must belong to exactly one field and to none of the extra keys. Each field must be dumped to a key that the model validates, or be required and have a plain validation key (e.g. `Field(alias="x", validation_alias="v")`). Every param of the latest version's endpoint and dependencies (including their dependencies) that reads the body must validate it in the same way, or else Cadwyn changes nothing in the body. These reach the latest version as they are: models in tuples, sets, frozensets, and deques (Cadwyn would have to replace them with lists, which strict schemas reject); root models at any depth (their validators get their data as a whole); models in bodies that a dependency reads in another way (e.g. `Annotated[list[Model], BeforeValidator(...)]` next to the endpoint's `list[Model]`); all bodies in apps with dependency overrides (`app.dependency_overrides`), because FastAPI builds the dependants of all dependencies again on each request of such apps, and checking them would build them once more, which runs code of users such as schema hooks; and all other models that don't meet the conditions above. The latest version reads them by their attributes as before, so they lose their extra keys, all of their fields count as set, and a field with an alias that differs from its name returns a 500 if it's required. If it's optional and the model doesn't validate its serialization alias (e.g. `Field(default=0, alias="x", validation_alias="v")`), it silently gets its default, because fixing it would change requests that pass today (#566).
* Uploads and forms: with FastAPI 0.158.2 or newer, when an optional form model was omitted and no other params read the form, a migrated body with a key named like the model param is treated as an already embedded body. If the model also has a field with that name (e.g. `body: str` in the model of `body: Annotated[Optional[MyModel], Form()] = None`), `request.body = {"body": "value"}` makes the latest version validate `"value"` as the whole model and fail. Set the embedded model explicitly, e.g. `request.body = {"body": {"body": "value"}}`. With FastAPI 0.158.2 or newer, FastAPI looks a form model and the other form params of the endpoint, its dependencies, and their overrides up in the same dict body for the latest version. Cadwyn gives each of them the value that FastAPI would give it for the migrated request, and the request fails with a 500 (`CadwynError`) when it can't: for a param that takes the whole body (e.g. `payload: dict = Body()` in an override), when a dependency declares the endpoint's form model and another param has its alias, and, after a request migration, when a param reads a key that the form model has taken under another name (e.g. through `AliasChoices`) or the migrated body of the form model isn't a dict. A param that reads a key of the form model gets the value of the migrated body as it is, e.g. an `int` where the form had a string. When the optional form model was omitted and other params read the form, a migration that supplies a dict with fields of the model also preserves the untouched form values for those params. A migration that supplies a non-null body without such fields in this case fails with a `CadwynError` naming the model param. Dependency form models keep aliases that FastAPI has not visited as extra fields, including later choices of `AliasChoices`; a model that forbids extra fields rejects these keys.
* `Json[...]` fields of request bodies: Cadwyn encodes their values for the latest version only if it can be sure that the latest version gets what the client has sent everywhere in the body. Otherwise, the latest version gets the body as it is, which fails with a 500 in every version unless a migration has encoded the values. It also parses the strings of `Json[...]` fields, which the request's version has parsed already, once more: `Json[str]` returns a 500 or another string, and a type that also accepts other JSON values (e.g. `Json[Any]`, `Json[Union[str, int]]`, or `Json[Optional[str]]`) gives the endpoint another value, e.g. `123` instead of `"123"` (#538). That's the case if:
    * a `Json[...]` value is a string that a migration sets (e.g. JSON that it has encoded already) or an empty string, is null, has a tuple in it, has a value of another type than the one its schema validates into (e.g. a value or an enum member that a migration sets), has a value that isn't JSON where its schema allows anything (e.g. a list that contains itself), has a NaN (JSON loses its sign), has a datetime or a time whose time zone JSON can't have (e.g. an offset with seconds), or has a dict whose keys have several types (e.g. `Union[int, str]`) or become the same in JSON
    * a `Json[...]` field is in a tuple, in the keys of a dict, in a model that refers to itself, in a model of a `list` or a `dict` body that the latest version gets as it is (see the request bodies that are lists or dicts of models above), or more than 8 models deep
    * a `Json[...]` value in a model of a `list` or a `dict` body (e.g. `list[Model]`) is a string: Cadwyn gets these models as FastAPI validates them rather than a dump, so it can't tell the strings that the client has sent from the ones that migrations set
    * the body has a union whose members aren't plain JSON values (e.g. models, `Json[...]` fields, decimals, dates, or constrained strings), validators (including the ones of pydantic types such as IP addresses and paths), serializers, `model_post_init`, computed fields, default factories other than builtin containers (e.g. `list`), an enum or a literal whose values aren't JSON values (e.g. decimals), an enum that looks its members up itself, a set, bytes, or a type that Cadwyn doesn't know (e.g. an `Iterable` or a `complex`)
    * a model in the body allows extra keys, changes or constrains strings in its config and has a union, or is dumped to keys that the latest version doesn't read (e.g. because of a serialization alias or `exclude=True`)
    * the body differs in any way between the request's version and the latest one (e.g. in a constraint of a string)
    * a dependency of the latest version reads the body as another type than the body param (e.g. `body: dict = Body()`), because it would read the JSON that Cadwyn encodes
    * a migration replaces a list, a dict, or a model with a value of another type (e.g. a tuple)
    * a dict on the way to a `Json[...]` value has keys other than strings, numbers, booleans, and null (e.g. UUIDs, enum members, or a subclass of `str` that a migration sets as a key of a model), because Cadwyn would have to hash and compare them, which can run code of users
    * the request has no body, so FastAPI gives the body param its default, which it doesn't validate, even if a migration sets the body
    * with FastAPI 0.158.2 or newer, a migration sets the body of an optional form model that the request doesn't supply

    Cadwyn can't know whether a string that a migration sets is JSON or a parsed value, so it only encodes the strings that the client has sent. Migrations get new copies of them, and Cadwyn treats a string as the client's only if it is still the very copy at the same place in the body (the same field, dict key, and list index). A migration that keeps such a string, or copies the body with `dict()` or `copy.deepcopy()`, keeps it. A string that a migration makes anew, even an equal one (e.g. with `.encode().decode()`), behaves as before, because Cadwyn can't tell it from JSON with the same text that the migration sets on purpose. For the same reason, if a migration calls `sys.intern()` on the client's string and then sets JSON with the same text through `sys.intern()` at the same place, Python gives it the client's very string, so the latest version gets that JSON as a string instead of decoding it. This needs `sys.intern()` on both strings. Python shares the empty string and some one-character strings (e.g. `"é"`, and with some versions of pydantic, such as pydantic-core 2.50.4, also `"5"`), so Cadwyn can't copy them. It treats them as the client's only if no request migration runs for the request, because then nothing can have changed them. If a migration runs, a body that still has such a string in a `Json[...]` field stays as it is, e.g. `"5"` becomes `5`. If a value in a `Json[...]` field makes Cadwyn leave the body as it is (the first case above), Cadwyn still encodes the strings that the client has sent, and only them, but only if each of them is still at its place or a migration has replaced it there with a value of its own. If a migration has moved one of them elsewhere (e.g. by reordering a list, renaming a dict key, or moving a model to another field) or removed it, the whole body stays as it is. So does it in the other cases above, e.g. if a migration replaces a list with a tuple, because the part that Cadwyn can't walk into might have strings that the client has sent.
* Schema instructions: diamond inheritance takes the field from the first base, like Pydantic does. A parent's rename reaches a subclass's own changes only through single, non-generic inheritance. A parent's rename of `x` to `y` doesn't fail at startup, and leaves both `x` and `y` in a subclass that declares `x` again, when a class between them changed `x` in a newer version and deletes it in the version of the rename (e.g. `schema(Middle).field("x").had(description=...)`, then `schema(Parent).field("x").had(name="y")` and `schema(Middle).field("x").didnt_exist` for `class Child(Middle)` with `x: int`). `had(default=PydanticUndefined)` doesn't make a field required when its default is declared in `Annotated[..., Field(default=...)]`. `didnt_have(...)` fails with an `AttributeError` when the attribute is a read-only property of an `Annotated` metadata object. `schema(Model).validator(...).existed` for a computed field fails on Python versions before 3.13.
* Defaults: Cadwyn versions the model classes, enum classes, and functions only within the lists, tuples, and dicts in defaults and other field attributes (see [Defaults](../concepts/schema_generation.md#defaults)). Everywhere else in them, they stay the latest ones in every version, e.g. in sets, frozensets, deques, `MappingProxyType`, the `default_factory` of a `defaultdict`, dataclass and model instances, and the args of `functools.partial` default factories. The copies that every version gets of subclasses of `list`, `tuple`, and `dict`, and of the containers that contain themselves, follow `copy.deepcopy()`: a custom `__deepcopy__` or `__reduce__` decides what the versions share with each other and with HEAD (e.g. a `__deepcopy__` that returns `self` shares the whole default), the objects within them get copied too unless their own `__deepcopy__` or `__reduce__` says otherwise (so e.g. a sentinel within them is another object in every version), `Counter` loses its attributes, and `deepcopy` can't keep the identity of some cycles through tuples and named tuples (e.g. with `xs = []; point = Point(xs); xs.append(point)`, `point[0][0] is point` isn't true in the copies).
* Alias instructions: when `.had(alias=...)` or `.didnt_have("alias")` renames the key of a field in an older version, data that has the old key but none of the keys that the field reads in that version fails with a `renamed_key` error (a 422 for requests, a 500 for responses). Cadwyn decides this from the data as it comes in, so it also fails when a validator of the model fills the field from other keys, such as a `model_validator(mode="before")` that copies a `compatibility_name` key into it.
* `cadwyn render` doesn't render `model_config`, and it renders `AliasChoices` and `AliasPath` as calls that raise a `TypeError`. It raises `CadwynRenderError` for recursive defaults, shared builtin or standard-library mutable defaults, subclass representations that print a builtin container literal instead of their type, extra instance attributes on `OrderedDict` or `Counter`, and `defaultdict` factories other than types, named Python functions, or `None`. Other subclasses keep their constructor and `__repr__` behavior; these must themselves reproduce their contents and state. Use a named `Field(default_factory=...)` function where needed (see [Rendering schemas](../concepts/schema_generation.md#rendering-schemas)). Subclasses of scalars such as `int` and `str` render as the base type.
* Computed fields of request bodies whose models override `model_dump()` (e.g. SQLModel models) still reach the latest version, which takes them as input: e.g. as extra keys, or as a 500 if the model forbids extra keys. Cadwyn can't tell whether an override takes `exclude_computed_fields` (SQLModel before 0.0.26 doesn't), so it calls it as before (#570).

## Rules for changing Cadwyn

**Scope**

* Fix the reported bug, not its neighbors.
* Bugs you find yourself go into an issue. Fix them only if a user reported them or they crash.
* Features that Cadwyn doesn't support, such as WebSockets, streaming endpoints, and migrations of `StreamingResponse` or `FileResponse`, aren't added as part of a fix.
* Don't widen a change during review. If a review uncovers a new problem, file it.
* Don't add options or flags to keep both behaviors unless the maintainer has signed off on them.
* If a simple workaround exists in user code and the fix in Cadwyn is complex, document the workaround instead.
* Rank review findings by how likely they are in real apps. A contrived case that breaks working output still gets fixed, but it shouldn't drive the design.
* Decide which breaking changes a major release takes when the work starts, not in the audit before the release. 8.0.0 rolled two fixes back and redesigned them late (#457 and #475, #458 and #474).

**What a change may alter**

* Compare every change against the last release, not against an idea of correct behavior.
* A change may alter output that is broken today: a crash, a 500, an empty or lost value. It may not alter output that works today, even if that output is wrong, unless the maintainer accepts it as a breaking change with an upgrade note in the CHANGELOG.
* OpenAPI of every version counts as output, including schema names.
* When behavior differs from the docs and clients rely on the behavior, a fix toward the docs is a breaking change. Warn about it at startup in the current major version, naming the model, the field, and how to keep working, and change the behavior in the next major version.

**How to fix**

* Prefer doing less. Narrow the fix, apply it only when the old path fails ("retry on failure", not an extra validation pass), or go back to the last release's code path.
* If every review round finds new edge cases in the same part of a fix, remove that part instead of patching it again.
* Don't reimplement FastAPI, Pydantic, or CPython logic. Call their functions, and evaluate annotations only where FastAPI itself does.
* Make safety checks allow-lists. Anything unknown takes the old behavior.
* Decide statically, not by the order in which models happen to be generated.
* Use one traversal to find what needs versioning and to copy it, never two that must agree. Finding must not copy, wrap, or rebuild the models that it leaves unchanged.
* Keep the user's objects as they are, and copy only what FastAPI or Pydantic would mutate. `deepcopy` isn't a way to isolate things: it goes through `typing`'s caches and breaks objects compared with `is`, such as FastAPI's sentinels.
* Caches may share structure but never user-visible state, such as a stateful default factory, between models or versions.
* Invalid instructions or models fail at startup with an error that names the model and the field. Never fail later at request time, and never serve wrong data silently.
* When you rely on a private FastAPI or Pydantic internal, check that it exists at import time and fail with a clear error if it changed. Never fall back silently.
* `Cadwyn()` accepts FastAPI's parameters and passes each of them to every router it creates.
* In the user docs, describe the common case and its workaround. The full list of shapes that a rule covers belongs in the tests.

**How to check a change**

* Run the same requests and OpenAPI of every version against the last release in its own checkout or virtual environment, and compare the results.
* Run the tests on the minimum supported and the latest Pydantic, and on Python 3.11 and 3.14. Check CI on every operating system before merging: recursion and stack limits differ on Windows and macOS.
* Pytest puts the root of the checkout it runs from first on `sys.path`, so run a test file from the checkout that you want to test.
* After merging `main` into a branch, look for top-level functions that are now defined twice. The later definition silently wins.
